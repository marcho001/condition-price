# 車輛密封投標系統 —— Phase 1 功能範圍

**日期**：2026-08-18
**用途**：需求主軸變更後，重新定義第一階段的功能範圍與系統邊界
**狀態**：範圍已確定，部分業務條件待確認（見第 8 章）
**前一版**：2026-08-07 Phase 1 功能範圍（已作廢，機制完全不同）

---

## 0. Phase 1 要做到哪裡

**只做「從收到車到決標通知」這一段，上游的回收流程與下游的收款過戶維持線下。**

### 0.1 跟 08-07 版差在哪

08-07 版的假設是公開競價拍賣平台；會議後確認實際需求是小圈子密封投標。

| | 08-07 版 | 本版 |
|---|---|---|
| 買方 | 不特定二手車商，需招募 | 固定 3–5 家長期合作廠商 |
| 車況資訊 | 標準化表單 + 內部評級 | 不評級。廠商自己來看實車 |
| 拍賣方式 | 定時開標為主，密封投標為輔 | 只有密封投標 |
| 底價 | 未達底價則流標或議價 | 不設底價，一律賣給最高價 |
| 目標 | 取得最高報價 | 快速去化為主，價格越高越好為輔 |

功能量約減少七成。保證金、信用額度、車況評級、議價、流標處理全部移除。

### 0.2 業務前提

- 買方是 3–5 家長期往來的廠商，家數固定，短期不會增加
- 廠商在出價前都會親自來看實車
- 不管能不能 cover 貸款欠款，都賣給最高價的人
- 若公司覺得價格偏低，會再問一次「有沒有人要加價」，這個動作沒有次數限制
- **本文件假設公司對這 3–5 家廠商的信任度高**，機制設計不以防弊為前提

### 0.3 系統邊界

整條業務鏈分四段，Phase 1 只做 B 和 C。

```
【A】上游            【B】內部端            【C】對外端           【D】下游
違約 → 收車    →    portal 拍賣模組   ↔   廠商投標站      →   成交後結案
                    (xstar-web-pc)       (獨立對外站)
另一 team 規劃       拍賣營運操作          廠商看車、投標        報價單、收款
                                                              過戶、交車
本系統不做          ★ Phase 1 做         ★ Phase 1 做        本系統不做
```

| 交接點 | 內容 |
|---|---|
| A → B | 另一模塊 submit「已收到車」後，該車出現在拍賣設定列表；車輛資料由既有 API 取得 |
| B/C → D | 決標通知送出後，本系統責任結束，後續轉線下 |

## 1. 使用者角色

### 1.1 公司內部（在 portal）

| 角色 | 主要工作 |
|---|---|
| 拍賣營運 | 車輛資料補充、發起投標、開標、決標、發起加價輪、看報表 |
| 系統管理員 | 廠商建檔、帳號開通與停用、參數設定 |

### 1.2 外部（在對外站）

| 角色 | 說明 |
|---|---|
| 合作廠商 | 看邀標的車、投價、看自己的紀錄 |

**一家廠商一個帳號，多人共用。** 不做主帳號／子帳號層級，不做註冊，帳號一律由內部開通。

代價（已知，不處理）：稽核只能到廠商層級，辨識不出實際操作人；密碼會被共用，離職員工仍握有密碼，因此內部必須能隨時重設密碼與停用帳號。

### 1.3 不對外揭露的資料

1. 內部參考價 / 貸款未償餘額
2. 成交金額（得標者知道自己出的價，落標者不知道成交價）
3. 其他廠商的出價金額

## 2. 上游：違約到收車 —— 本系統不做

由另一個 team 的 PM 規劃，本文件未參與，以下僅為大致理解，**不作為規格依據**。

```
逾期 → 催收 → 違約判定 → 決定回收 → 車輛取回 → 入庫點交 → submit「已收到車」
                                                                    ↓
                                                          交接到區塊 B（本系統）
```

本系統對這一段的唯一依賴是：該模塊要能 submit「已收到車」，並讓本系統取得車輛資料。其餘一概不涉入、不呈現、不驗證。

需要跟該 team 對齊的交接介面：

| 項目 | 要確認的 |
|---|---|
| 事件觸發 | 「已收到車」是哪個模塊的哪個動作？狀態值叫什麼？ |
| 資料取得 | 透過哪個 API 取？回傳哪些欄位？ |
| 可處分性 | 「這台車確定可以賣」由誰、在哪一步確認？本系統不驗證 |
| 逆向情境 | 收車後被撤回或借款人贖回，該模塊會不會發事件？本系統目前不接 |
| 時間差 | 從 submit 到可以發起投標，中間還有沒有必要步驟 |

## 3. 內部端功能 —— 做在 portal（xstar-web-pc）

既有內部 portal 新增一個拍賣模組。內部人員不需要第二個網址、第二組帳號，權限與選單沿用現有機制。

### 3.1 從收到車到排上拍賣

```
① 別的模塊 submit「已收到車」
        ↓
② 該車出現在拍賣設定列表，狀態＝待設定
        ↓
③ 拍賣營運檢視從貸款申請帶過來的車輛資料
        ↓
④ 補資料（選配，可以不補）
        ↓
⑤ 排定拍賣：勾選邀請名單 + 設定起迄時間 + 送出
        ↓
   狀態 → 投標中，對外站同步出現這台車，廠商收到邀標通知
```

第 ④ 步是選配的，資料不補也能直接排上拍賣，系統不擋。車輛頁顯示「目前幾張照片 / 哪些欄位是空的」作為軟性提示，不做強制檢核。

### 3.2 拍賣設定列表

| 項目 | 說明 |
|---|---|
| 列表欄位 | 車牌、廠牌車型年份、入庫日、狀態、目前輪次、投標家數、截止時間、剩餘時間 |
| 篩選 | 依狀態、廠牌、入庫日區間 |
| 排序 | 最新入庫 / 截止時間最近 |
| 提醒標記 | 待設定超過 N 天、截止前 24 小時仍無人投標 |

### 3.3 車輛資料

主要來源是貸款申請時的既有資料，透過 API 取得，不重新輸入。

| 類別 | 內容 | 來源 |
|---|---|---|
| 基本規格 | 車身號碼、車牌、廠牌、車型、年份、里程、排氣量、燃料、變速箱、驅動方式、顏色、座位數 | 貸款申請既有資料 |
| 內部參考價 | 貸款未償餘額或估值。只顯示、不擋成交，用途是事後算回收率。廠商看不到 | 貸款／貸後既有資料 |
| 照片 | 多張上傳，無張數下限 | 內部補充（選配） |
| 備註 | 自由文字，記錄明顯瑕疵或需說明事項 | 內部補充（選配） |

補充欄位的最終清單待定（見 8.3），Phase 1 先做照片 + 備註。

不做車況評級、標準化車況表單、車體傷痕圖 —— 廠商會親自來看實車。

車輛狀態：`待設定` → `投標中` → `加價中` → `已決標` → `已結案`，另有 `封存`。刪除一律用封存。

### 3.4 排定拍賣

| 項目 | 說明 |
|---|---|
| 邀請名單 | 勾選，預設全選 |
| 起迄時間 | 由內部自行設定開始日與截止日，系統只帶預設值（預設 2–3 天，見 8.4） |

送出後對名單內廠商發通知，狀態轉「投標中」。

### 3.5 投標進行中

截止前，內部看得到：哪些廠商已投標、哪些還沒、倒數時間。**看不到出價金額。**

實作方式：後端不加密儲存，僅前端 UI 在截止前不顯示金額。含意是「截止前看不到金額」屬於作業規範，不是技術保證——有資料庫或後端權限的人仍看得到。

催投：對尚未投標的廠商發即將截止通知，可手動觸發，也可設定截止前 N 小時自動發送。

### 3.6 開標與決標

截止時間到，內部看得到完整排名、各家金額、投標時間、修改歷程。

動作二選一：

- **決標**給最高價者 → 狀態轉「已決標」，發出得標／未得標通知 → 轉線下
- **發起加價輪** → 見 3.7

無人投標：本次投標未成立（無底價概念，不使用「流標」），車輛回到「待設定」，可重新發起。

同分：投標時間較早者優先，系統直接判定。

### 3.7 加價輪

輪數不限，每一輪結束後都可以再開下一輪。

| 項目 | 規則 |
|---|---|
| 觸發 | 拍賣營運手動一鍵觸發，無次數上限 |
| 狀態 | 觸發後車輛狀態轉為「加價中」 |
| 邀請對象 | 預設全體受邀廠商，可勾選調整（見 8.2） |
| 理由 | 必填，下拉選單（價格偏低 / 前幾名接近 / 其他）+ 選填備註 |
| 起迄時間 | 內部自行設定，系統帶預設值（24 小時）可改 |
| 出價規則 | 只能加不能減。不出價視為維持原出價；第一輪沒投標者不出價就是沒有出價 |
| 結果 | 本輪截止後，就全體廠商的最新有效出價重新排名，最高者暫居第一 |
| 每輪結束 | 內部二選一：決標 / 再開一輪 |

**編輯訊息後送出**（需求方明確點名要的互動）：

1. 內部按「發起加價輪」
2. 系統依模板產生訊息草稿，帶入目前最高價
3. 內部可在送出前直接編輯整段文字
4. 設定本輪起迄時間
5. 送出給勾選的廠商（Email + 站內通知），訊息內附拍賣連結

模板可帶入的變數：車輛資訊、目前最高價（不揭露是誰出的）、投標家數、你目前的出價（逐家帶入）、本輪截止時間、拍賣連結。

每一輪留存：輪次序號、起迄時間、邀請名單、觸發理由與備註、操作人、送出的訊息全文、各家出價與時間。車輛頁顯示「本車目前第 N 輪」。

### 3.8 廠商與帳號管理

- 廠商建檔：名稱、聯絡人、聯絡方式、啟用 / 停用
- 帳號由內部開通，可重設密碼、停用

### 3.9 報表

| 指標 | 用途 |
|---|---|
| 平均投標家數 | 有效參與程度 |
| 各家出價分布 | 定價與行情參考 |
| 各家得標次數 | 往來分布 |
| 加價輪觸發率、平均輪數 | 營運習慣自我檢視 |
| 各輪平均加價幅度 | 判斷第幾輪之後沒有邊際效益 |
| 回收率（成交價 ÷ 內部參考價） | 帳務面 |

### 3.10 通知（內部收）

投標截止、無人投標、每一輪結束、車輛待設定超過 N 天。

## 4. 對外端功能 —— 獨立的廠商投標站

### 4.1 為什麼另開一站，不做在 portal 裡

| 理由 | 說明 |
|---|---|
| 安全邊界 | portal 內有借款人個資、貸款餘額、催收紀錄，這些絕對不能對廠商揭露。分開部署是架構上就到不了，同一套系統則等於「權限設定從沒出過錯」 |
| 認證體系 | 內部是員工帳號；廠商是外部帳號，需要獨立的密碼政策、鎖定、忘記密碼流程 |
| 網路邊界 | portal 可只在內網／VPN；對外站必須公網暴露，需要獨立防護與發版節奏 |
| 使用者性質 | portal 是給受訓過的內部人員用的重表格後台；廠商一年只用幾十次，需要極簡介面 |

後端拍賣核心與資料共用，兩個前台各自呈現各自該看到的部分。

### 4.2 頁面

| 頁面 | 內容 |
|---|---|
| 登入 | 帳號 + 密碼。未登入不揭露任何車輛資訊 |
| 首次登入：條款同意 | 邀標條款，內容待確認（見 8.5） |
| 拍賣列表 | 目前邀請我投標的車：縮圖、廠牌車型年份、里程、狀態、截止倒數、我的出價狀態 |
| 車輛詳情 | 規格、照片、備註、截止時間、投標入口 |
| 投標 / 改價 | 單一金額欄位。截止前可修改，次數不限 |
| 加價輪投標頁 | 同詳情頁，額外顯示目前最高價、我目前的出價、本輪截止時間；金額只能填高於自己原出價的數字 |
| 我的投標紀錄 | 投過的車、金額、時間、結果（得標 / 未得標＋名次） |
| 站內通知 | 邀標、即將截止、加價輪、得標、未得標 |
| 結果頁 | 得標顯示自己的成交金額與後續聯絡方式；未得標顯示名次，不顯示任何金額 |

**手機優先**（裝置習慣待確認，見 8.1，確認前先假設手機優先）。

### 4.3 加價輪在廠商端的流程

```
① 內部 submit 發起加價輪
        ↓
② 拍賣狀態轉為「加價中」
        ↓
③ 受邀廠商收到 Email（＋站內通知）：
   「本車目前價格已到 xxx，還想再加價嗎？」＋ 拍賣連結
        ↓
④ 點連結進入 → 看到目前最高價、自己目前的出價、本輪截止時間
        ↓
   ├─ 更新出價（只能往上加）
   └─ 不動作 → 維持原本出的價
        ↓
⑤ 本輪截止 → 全體最新有效出價重新排名，最高者得
        ↓
   內部二選一：決標 / 再開一輪（回到 ①）
```

廠商看得到目前最高價的金額，看不到是誰出的。

### 4.4 通知（廠商收）

| 事件 | 條件 |
|---|---|
| 新的邀標 | 被列入邀請名單 |
| 即將截止 | 只發給尚未投標者 |
| 加價輪邀請 | 內容可由內部編輯後送出，含拍賣連結 |
| 得標 | |
| 未得標 | 含名次，不含任何金額 |

管道：Email + 站內通知。實際管道待確認（見 8.1）。

### 4.5 截止判定

採最簡方式：以伺服器時間為準，截止後送出的投標一律拒絕，不設寬限期，不做自動延長。前端倒數以伺服器時間校正。

## 5. 下游：成交之後 —— 本系統不做

流程尚未釐清。本系統在決標通知送出後即結束責任。

```
決標 → 廠商提供正式報價單 → 收款 → 過戶 → 交車 → 結案
```

| 項目 | Phase 1 |
|---|---|
| 決標通知（雙方） | 做 |
| 決標結果留存（廠商、金額、時間） | 做 |
| 車輛狀態標記已決標 → 手動改已結案 | 做 |
| 報價單上傳／比對 | 不做 |
| 收款、金流、對帳 | 不做 |
| 過戶、文件、交車點交 | 不做 |
| 付款逾期、棄標處理 | 不做（見 8.6） |

「已結案」是內部手動勾選的狀態，系統不驗證是否真的收到錢、過完戶。

這一段釐清後會回頭影響本系統的事：付款期限（決定要不要做逾期提醒）、得標不付款的處理（決定要不要補「給第二名」路徑）、報價單是否需入系統留存、成交價含稅與否（影響回收率算法）。

## 6. 資訊揭露規則

| 資訊 | 廠商自己 | 其他廠商 | 內部 |
|---|---|---|---|
| 自己的出價金額 | 看得到 | 看不到 | 截止後看得到 |
| 其他家的出價金額 | 看不到 | — | 截止後看得到 |
| 本次投標家數 | 開標後看得到 | — | 全程看得到 |
| 誰被邀請了 | 看不到 | — | 看得到 |
| 加價輪的目前最高價 | 看得到（金額） | — | 看得到 |
| 加價輪最高價是誰出的 | 看不到 | — | 看得到 |
| 本車跑到第幾輪 | 看得到 | — | 看得到 |
| 成交金額 | 得標者知道自己的 | 看不到 | 看得到 |
| 自己的名次 | 看得到 | — | 看得到 |
| 內部參考價 / 貸款餘額 | 看不到 | 看不到 | 看得到 |

**稽核**：出價金額的查看與修改留紀錄；每一輪加價輪的觸發人、時間、理由、訊息全文留紀錄。外部端要不要留投標稽核（IP / 裝置）見 8.5。

## 7. 明確不做的

| 不做 | 原因 |
|---|---|
| 車況評級、標準化車況表單、車體傷痕圖 | 廠商自己來看實車 |
| 定時開標（英式競價） | 只做密封投標 |
| 加價單位、自動延長、立即成交價 | 定時開標的配套 |
| 議價 / 商談 | 被加價輪取代 |
| 底價與流標判定 | 一律賣給最高價 |
| 保證金與信用額度制 | 3–5 家長期合作夥伴。副作用見 8.6 |
| 系統強制的輪數上限 | 需求方要求不限次數 |
| 密封價的加密儲存 | 只需前端 UI 看不到（見 3.5） |
| 撤標 / 作廢投標 | 上架前已由業務端確認可處分 |
| 廠商註冊、主子帳號、出價額度 | 一家一個共用帳號，由內部開通 |
| 金流、過戶、交車、報價單 | 見第 5 章 |

**撤標的代價**（記錄在案，不處理）：投標進行中若真的發生贖回，系統沒有處理路徑，只能人工對廠商說明，車輛狀態由管理員手動改回「待設定」或「封存」。若實務上發生過一次，再回頭補「作廢本次投標」。

## 8. 待確認事項

打★的兩項會直接影響機制能不能運作，建議優先釐清。

### 8.1 ★ 廠商操作習慣與通知管道

- 用手機還是電腦？（本版先假設手機優先）
- 平常怎麼聯絡？**會看 Email 嗎？** 還是 LINE / 電話？
- 加價輪的核心互動就是「發訊息 + 附連結」。如果廠商實務上不看 Email，這套機制會做出來但收不到，是目前最高的單點風險
- 加價輪的訊息模板要幾套？一套讓內部改，還是多套可選？

### 8.2 加價輪的邀請對象

本版預設「全體受邀廠商」，另一選項是「只邀前一輪投標者」。

| 比較項 | 只邀前一輪投標者 | 邀請全體廠商（本版預設） |
|---|---|---|
| 投標家數 | 限縮在原本就投標的 2–3 家 | 可能把原本沒空看車的廠商拉進來 |
| 對第一輪的影響 | 沒投標就進不了加價輪 | 沒投標也不會錯過（見 8.7） |
| 資訊揭露 | 目前最高價只給已投標者 | 也給完全沒參與的廠商 |
| 沒看過實車的廠商 | 不適用 | 可能在沒看車的情況下出價 |
| 去化速度 | 較快 | 較慢，等於再給一次看車時間 |
| 實作 | 名單＝前一輪投標者 | 名單＝原邀請名單 |

系統兩案都支援（名單本來就可勾選調整），這題實際上只是在決定**預設帶出誰**。

要問需求方：現行線下實務上，「再問一次要不要加價」是問全部人，還是只問出過價的人？

### 8.3 車輛資料要補哪些欄位

貸款申請既有資料以外還要補什麼？目前認定沒幾項，Phase 1 先做照片 + 備註。要不要規定最少幾張照片？

### 8.4 邀標到截止的預設天數

起迄時間已確定由內部自訂，這題只剩系統預設值填多少。本版預設 2–3 天。廠商需要時間安排看車，預設值太短會讓營運習慣性壓縮期限。

### 8.5 對外端的稽核記錄與邀標條款

- **外部端投標要不要留稽核記錄**（IP、裝置、時間）？注意因為一家一個共用帳號，這份記錄只能證明「這家投的」，證不出是誰投的
- **首次登入的邀標條款內容是什麼？誰擬？** 至少要含「本公司保留發起加價輪的權利」。要不要含：投標不可撤回、得標後的付款義務、車況現況交車、爭議處理方式？條款改版後要不要重新同意？

### 8.6 ★ 得標不付款怎麼辦

保證金制度砍掉後，系統對違約沒有制裁手段。這題屬於下游，但答案會決定本系統要不要補功能。

- 目前有沒有遇過得標後不付款、不來牽車的？怎麼處理？
- 付款期限訂多久？逾期怎麼辦？幾天視為棄標？
- 棄標後車輛怎麼處理（重發投標？直接給第二名？）若要給第二名，本系統要補：保留完整排名、二次決標、第二名通知

### 8.7 廠商壓價等加價輪的可能性

本版假設對廠商信任度高，機制不以防弊為前提，**因此暫不處理**。列在這裡是為了記錄在案：

加價輪輪數不限、且開放給沒投標的廠商，理論上會讓「第一輪先出試探價、等後面加價輪」變成划算的策略。若日後觀察到第一輪出價普遍偏低、或第一輪未投標而加價輪才進來的次數變多，再回頭處理。屆時可用的手段：限制加價輪只邀前一輪投標者、降低觸發頻率、對輪數設上限。

需要的話，報表可加一個指標：第一輪未投標、加價輪才進來投標的次數。

### 8.8 業務量與名單

- 每月回收幾台？平均車價區間？
- **同時在架的車通常有幾台？** 若常態只有 1 台，拍賣列表頁的價值很低，會影響附錄 A 的方案選擇
- 從 submit 收到車到可以發起投標，中間要多久？
- 廠商名單會不會變動？誰有權增減？

### 8.9 其他

| 項目 | 本版設計 | 要確認的 |
|---|---|---|
| 隱藏廠商身分 | 保留匿名 | 廠商彼此都認識，需求方是否在意？不在意的話，開標後可對廠商顯示參與者名單（仍不含金額） |
| 未得標者的名次 | 顯示名次，不顯示金額 | 若需求方連名次都不想給，落標通知只顯示「未得標」 |

## 附錄 A：對外端兩個方案的比較

供會議向需求方確認。Phase 1 暫定採方案二，方案一由其他同事另行評估。

- **方案一：一次性簽章連結** —— Email／訊息附帶簽章連結，廠商點開直接進投標頁，不需帳號密碼
- **方案二：帳號登入** —— 廠商用內部開通的帳號密碼登入，站內有列表、詳情、投標、我的紀錄

| 比較項 | 方案一：一次性連結 | 方案二：帳號登入 |
|---|---|---|
| 廠商操作成本 | 點連結即到投標頁，零記憶 | 需記帳號密碼，一年只用幾十次，久沒用會忘 |
| 開發範圍 | 約 3 頁，無登入、無 session、無密碼流程 | 登入、忘記密碼、列表、詳情、投標、我的紀錄、通知、條款 |
| Phase 1 工期 | 明顯較短 | 較長 |
| 拍賣列表頁 | 做不到（連結只帶一台車） | 有 |
| 我的投標紀錄 | 做不到 | 有 |
| Email 送不到的後果 | 致命，完全無法投標且無自救途徑 | 可救，廠商仍可自行登入查看 |
| 憑證外流 | 連結即憑證，轉發即可投標，需綁單次與時效 | 密碼即憑證，一家共用一組 |
| 加價輪 | 每輪需重發新連結、舊連結要失效 | 發通知即可，連結指向同一頁 |
| 帳號維護 | 無 | 內部需開通、停用、重設密碼 |
| 未登入的資訊防護 | 無「未登入牆」 | 未登入完全看不到車輛資訊 |

**三個決定性問題**

1. **同時在架通常有幾台車？**（8.8）常態 1 台 → 列表頁沒價值，方案一的最大缺點消失；常態 3 台以上 → 方案二明顯較好
2. **廠商需不需要回頭查自己的投標紀錄？** 需要 → 方案二
3. **Email／訊息的送達可靠度？**（8.1）不可靠 → 方案一直接失效

**補充**

- 兩案並非互斥，可先做方案一、日後再補登入。但並存等於兩套入口都要維護，Phase 1 不建議
- 兩案的後端拍賣核心完全相同，差別只在對外前台與身分驗證方式，先做哪個都不浪費後端的工
